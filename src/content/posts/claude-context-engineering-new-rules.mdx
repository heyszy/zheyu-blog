> 本文源于 Anthropic 技术团队成员 Thariq Shihipar 在 X 上发布的《The new rules of context engineering for Claude 5 models》。

我们习惯把 AI 开发效果不好归结为提示词没写好。于是，需求写得越来越长，规则列得越来越细，项目里的 `CLAUDE.md`、Skills 和系统提示词也不断膨胀。

Claude Code 团队最近做了一个反常识的实验：面对 Opus 5、Fable 5 这一代新模型，他们删掉了 Claude Code 系统提示词中超过 80% 的内容，编程测试结果却没有出现可衡量的性能下降。

这不是在说提示词不重要，而是说明模型能力变强之后，旧的上下文工程方法可能已经过时。那些曾经用来避免模型犯错的规则，今天反而可能让它花更多精力处理重叠和冲突的指令。

<h2 id="context">提示词只是上下文的一小部分</h2>

向 Claude 发送一条消息时，模型看到的不只有这条提示词。系统提示词、项目说明文件、Skills、记忆、工具定义和当前会话，都会共同进入它的工作上下文。

Anthropic 把组织这些信息的工作称为“上下文工程”。提示词通常服务于某一次具体请求，上下文则会跨越许多任务反复生效。问题也由此出现：你很难提前知道用户会问什么，却试图用一套固定规则覆盖所有情况。

在旧模型能力有限时，写死规则是一种务实选择。比如，为了避免 Claude 生成冗长或错误的注释，系统提示词可能直接规定：默认不写注释，不写多行注释块，也不要主动创建规划和分析文档。

这样的规则能避免最坏情况，却会误伤正常需求。复杂代码可能确实需要多行注释，团队也可能有自己的文档规范。更麻烦的是，当系统提示词说“不要加注释”，项目文件说“适当补充文档”，用户又明确要求解释关键逻辑时，模型必须先判断应该听谁的。

新模型已经更擅长理解意图和环境。Claude Code 团队因此把原来的长规则缩成一句话：让代码读起来像周围的代码，匹配现有项目的注释密度、命名和惯用写法。

规则少了，要求反而更准确。

<h2 id="principles">六条正在发生变化的上下文工程原则</h2>

### 1. 少制定通用规则，多让模型结合现场判断

项目说明文件应该记录真正特殊的约束，而不是重复常识。比如，“所有类型只能定义在同一个文件中”是代码库特有的规则，值得明确写下；“修改后记得检查代码”则过于宽泛，模型通常已经知道。

判断一条规则是否值得保留，可以看两个问题：它是否来自项目里真实发生过的错误？模型能否仅靠阅读代码和目录结构自行得出？如果没有具体失败案例，而且模型很容易从现场看出来，这条规则大概率只是在占用上下文。

### 2. 少给工具使用范例，多把工具接口设计清楚

过去常见的做法是给模型准备大量工具调用示例。新模型很容易把这些示例理解为行动边界，只在示例展示过的范围内探索。

更有效的做法是把接口本身设计好。参数名称要清楚，可选值要能表达状态，工具描述要说明关键约束。比如，任务状态只有 `pending`、`in_progress` 和 `completed` 三种，同时规定“只能有一个任务处于 `in_progress`”，模型就已经能据此理解完整的工作方式。

好的接口本身就是提示词，而且比一长串例子更稳定。

### 3. 不要一次性给出所有知识，改用渐进式披露

代码审查、上线验证、安全检查都很重要，但不是每个请求都需要同时加载这些说明。Anthropic 的做法是把它们拆成独立 Skills，由 Claude 在相关任务出现时再读取。

工具也可以延迟加载。模型先看到简短的能力索引，需要使用某项工具时，再搜索并读取完整定义。这样既能提供足够多的能力，也不会让所有工具说明一直挤在上下文里。

同样的思路适用于项目文档。根目录说明文件只做导航和记录关键陷阱，详细的测试、发布、数据库或界面规范分别放进对应文档，需要时再加载。

### 4. 同一条要求不要到处重复

早期模型有时会忽略上下文前部的信息，所以团队会在系统提示词、工具描述和项目文件中重复同一条要求。如今，这种做法的收益已经降低，冲突风险却一直存在。

工具怎么用，就写进工具描述；仓库的特殊约束，写进项目说明；某类工作的完整流程，放进对应 Skill。每条信息尽量只有一个权威位置。

### 5. 不要再把项目说明文件当作记忆仓库

过去，人们会不断把经验追加到 `CLAUDE.md`。时间一长，临时结论、个人偏好、项目约束和操作流程混在一起，文件越来越难维护。

现在的 AI 开发工具通常已经提供自动记忆或独立的持久化机制。项目说明文件可以回到原本的职责：解释仓库用途，记录从代码表面看不出来的约束，并为更详细的资料提供入口。

### 6. 与其写抽象描述，不如提供高保真参考资料

模型越来越善于理解复杂参考资料。一套测试可以充当规格说明，另一个代码库里的函数可以成为移植范例，HTML 原型可以表达界面结构和交互，评分标准可以交给独立的验证智能体。

在界面开发中，一份可运行的 HTML 原型通常比几段文字或一张截图更有用。它不仅展示最终外观，还包含布局、层级、状态和交互信息。代码与测试之所以有效，是因为它们减少了自然语言中的歧义。

<h2 id="change">我们该如何改变</h2>

第一，是时候给自己的 AI 配置做做减法了。模型升级后，过去为了补偿旧模型弱点而写下的规则，不一定还需要保留。可以挑一类常见任务，用精简前后的配置各跑几次，比较正确率、返工次数和执行成本，再决定是否删除。不要因为一条规则存在很久，就默认它仍然有效。

第二，把项目说明从“百科全书”改成“入口地图”。一份实用的 `AGENTS.md` 或 `CLAUDE.md`，只需回答几件事：这个仓库做什么，有哪些不容易看出来的限制，常用验证入口在哪里，哪些详细规范需要按需读取。目录结构、语言版本、常见命令等能自动发现的信息，不必逐项复述。

第三，遇到 AI 反复做错，不要立刻再加一句禁止事项。先判断问题来自哪里：缺少事实，就补参考资料；工具不好用，就改接口；验收标准含糊，就补测试或评分标准；只有在模型明知要求仍反复违反时，才值得新增规则。

第四，把验证材料当成上下文的一部分。让 AI“做得好一点”很难执行，给它测试、截图、设计原型、输入输出样例和验收清单，它才知道什么叫完成。对于长期任务，清晰的参考资料通常比更长的提示词更有价值。

第五，避免在多个层级表达相同要求。系统提示词、项目说明、Skill、工具描述和用户请求应当各有职责。重复不仅浪费上下文，还可能因为措辞稍有差异制造冲突。

<h2 id="focus">上下文工程的重点变了</h2>

早期的上下文工程更像是在给模型安装护栏，堆砌规则、划定项目边界，最好再配几个示例。新模型的能力提升后，重点逐渐转向信息架构：什么内容应该常驻，什么内容按需加载，哪类知识应该放进工具，哪些要求应该交给代码和测试表达。

日常 AI 开发也可以从一个简单动作开始：打开自己的 `AGENTS.md`、`CLAUDE.md` 和 Skills，逐条检查哪些内容仍然解决真实问题，哪些只是旧模型时代留下的补丁。

留下项目独有的知识，删掉模型已经能够自行判断的常识，再把细节放到真正需要它们的地方。
